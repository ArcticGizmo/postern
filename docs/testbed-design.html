Postern · testbed proposal · 30 Oct 2026

Sallyport

A companion app that sends a library of real-shaped requests through Postern from its own window, in its own process, against a sandbox Postern that can only ever reach a fake on 127.0.0.1.

FEASIBLE
Yes, and most of the plumbing is already in the repo. Postern.Client is the library a real app would use, fake-upstream is a GitHub-shaped stand-in, --pipe and --data-dir already isolate a run, and smoke.ps1 already crashes Postern under a client. What's missing is a profile that can't touch real credentials or real hosts, a fake that speaks more than GitHub, and a window to drive it all from.

The name: a sally port is the other small gate in a castle wall, the one defenders used to send sorties out and see what came back. It fits next to Postern, and the app's whole job is sending sorties. Rename freely.

The picture

Three processes, one fence

Each box is its own exe with its own window or tray icon, so killing one shows exactly what the others see. Your installed Postern and Postern (Dev) sit outside the fence on their own pipes and are never involved.

What gets built

Four pieces, two of them half there

extends Profile

A Sandbox profile

A third profile beside Live and Dev, started with --sandbox (or .\testbed.cmd). Same idea as Dev, with the doors welded shut.

  • Pipe postern-sandbox, data in Postern.Sandbox\
  • Credentials namespaced postern-sandbox:
  • Refuses any base URL that isn't loopback
  • Seeds connections and dummy credentials on first run
  • Sand-coloured tray icon, "(Sandbox)" in every title
grows fake-upstream

testbed-upstream

Today's fake speaks GitHub only. It grows a route prefix per service and a few knobs you can flip from Sallyport.

  • GitHub, Jira, Slack, Octopus and Anthropic shapes
  • Pagination, ETags, redirects, SSE, gzip, big bodies
  • Knobs: latency, 429, 500, hang, drop the connection
  • /_seen: the last N requests as it received them
new exe

Sallyport

An Avalonia window in tools/Postern.Sallyport. It references Postern.Client and nothing else from the solution, so it behaves exactly like a third-party app.

  • Scenario library, each with an expected outcome
  • Run one, run all, or soak at a steady rate
  • Shows Postern's answer beside what upstream saw
  • --run-all for a headless pass in CI
new page, sandbox and dev only

Testbed page in Postern

A nav item that only exists outside Release builds. It shows the sandbox's state and launches the other two as separate processes.

  • Open Sallyport, start or stop the upstream
  • Reset sandbox: wipe data and postern-sandbox:*
  • Launch with UseShellExecute so nothing inherits Postern's console or dies with it

When Postern goes down

    
Four drills, run from Sallyport

    
Sallyport can do this safely because it only ever acts on the sandbox's pid, which it reads from the same status call postern-cli uses. It runs with a soak going, so each drill leaves a visible trace in the strip and the event log.

    

      
Crash
Kill the Postern process while the supervisor is watching.
One or two amber cells while the client retries, a new pid within about 2 s, no new approval prompt.

      
Quit
Ask Postern to exit cleanly, with no supervisor to bring it back.
Red cells and PosternUnavailableException until you start it again; then it carries on with the same token.

      
Revoke mid-soak
Revoke Sallyport on Postern's Apps page while it's sending.
The next request gets app-revoked at once. Sallyport doesn't ask to register again by itself.

      
Wait for start
Start Sallyport with Postern not running.
It shows "waiting for postern-sandbox" using WaitUntilAvailableAsync, and registers as soon as the pipe appears.

    

  


  

    
Why it's safe

    
Rails that hold even when you're careless

    

      
Loopback only, enforced by the broker
In the Sandbox profile, the connection validator rejects any base URL whose host isn't 127.0.0.1, ::1 or localhost, and the forwarder checks again per request. It fails closed with sandbox-host, so a pasted real URL produces an error, not a call.

      
Fake credentials, real ones refused
Seeded values are obviously fake (sandbox-not-a-secret-01). The credential dialog and postern-cli credential set refuse anything shaped like a real token: ghp_, github_pat_, glpat-, xox, sk-, sk-ant-. Even if one got in, the loopback rule means it could never be sent anywhere.

      
Its own pipe, data and namespace
Same mechanism as Dev: postern-sandbox, Postern.Sandbox\ and postern-sandbox:* in Credential Manager. A sandbox can't read, change or delete what Live or Dev hold.

      
Sallyport refuses other pipes
It connects to postern-sandbox by default, and to postern-dev only behind a red banner. It won't start against postern at all, so it can never put scenario traffic through your real credentials.

      
Nothing ships
Sallyport, testbed-upstream and the Testbed page are excluded from Release builds and the installer, the way --dev-auto-approve already is.

      
Reset is one click
Reset deletes Postern.Sandbox\ and every postern-sandbox:* credential, then seeds again. The next run starts from a known state.

Your call

    
Decisions before building

    

      
A real Sandbox profile, or Dev with flags?
Dev plus --pipe and --data-dir already isolates data, but credentials still land under postern-dev: and nothing stops a real host.
Leaning: a real profile. The loopback rule is what makes it safe, and it needs a profile to hang off.

      
Should Sallyport be able to kill Postern?
It's the quickest way to run the drills. It also means a tool holding a "kill the broker" button, even if only for the sandbox pid.
Leaning: yes, sandbox pid only, checked against the pipe's published broker path before killing.

      
Auto-approve Sallyport?
--dev-auto-approve sallyport makes runs faster. Leaving the prompt in tests the prompt every time.
Leaning: prompt in the window, auto-approve in --run-all.

      
Beyond .NET?
Sallyport exercises Postern.Client. The Node and PowerShell paths from How it works would need their own small runners.
Leaning: later. Keep the scenario JSON language-neutral so a Node runner can read the same files.
